# 문서 PR 작성

## 변경 범위 확인

- 저장소의 `AGENTS.md`, `README.md`와 `.github/pull_request_template.md`를 읽는다. README에 브랜치 규칙이 있으면 따른다.
- 현재 브랜치, 작업 트리, 원격 저장소와 대상 base 브랜치를 확인한다. base와 작업 브랜치의 커밋 목록 및 전체 diff를 읽고 PR에 들어갈 최종 변경을 파악한다.
- 커밋되지 않은 내용은 PR 변경에 포함된 것으로 설명하지 않는다. 스테이징·커밋·브랜치 분리는 사용자가 요청한 범위에서만 수행한다.
- 독립적인 PR은 서로의 변경을 포함하지 않게 구성한다. 의존성이 있으면 본문에 명시한다.

## 제목과 본문

- PR 제목은 `<type>(<scope>): <summary>` 형식으로 작성하고 scope를 반드시 포함한다. 유형과 허용 scope 목록은 [커밋 규칙](../commit/SKILL.md)의 메시지 형식을 참조한다.
- scope는 PR 전체의 주목적을 기준으로 선택한다. 포함된 커밋의 scope가 모두 같을 필요는 없다. 요약은 변경 결과가 드러나는 간결한 한국어로 작성한다.
- PR 템플릿의 항목을 사용한다. 기획·설계 초안 등록, 현재 기준 변경, 과거 논의·평가 기록 중 무엇을 하는지 설명한다.
- 주요 내용에 결정 근거나 관련 회의·평가·기준 문서를 연결한다. PR 본문의 파일 링크는 해당 원격 브랜치에서 열리는 주소를 사용한다.
- 초안 등록을 합의 완료로 표현하지 않는다. 문서 상태와 변경할 기준, 미정 사항 및 검토 질문을 구분한다.
- PR을 읽는 사람이 이해하는 데 필요한 배경만 남긴다. 사용자가 제공한 작업 배경은 목적에 연결하되 대화 과정을 나열하지 않는다.
- 실제 확인한 검사만 완료로 표시한다. 링크·형식 검사와 기술 성능·라이선스 검증을 구분하고, 렌더링 등 확인하지 못한 항목은 명시한다.
- 안내용 HTML 주석은 완성된 PR 본문에서 제거한다. 단순 형식 수정은 템플릿 안내에 따라 항목을 줄인다.

## GitHub 반영

- 본문 작성만 요청한 경우 게시하지 않는다. PR 생성·수정 요청에 push가 필요한 경우 요청된 브랜치만 올리고, 기존 승인이 있으면 다시 확인을 요구하지 않는다.
- `gh` 사용 전 인증 상태와 대상 저장소를 확인한다. 인증 정보는 출력하거나 본문에 기록하지 않는다.
- 생성 전 동일한 head와 base의 열린 PR이 있는지 확인한다. 기존 PR이 있으면 중복 생성하지 않고 요청 범위에 따라 갱신한다.
- 제목, 본문과 base·head를 확정한 뒤 실행한다. 본문은 임시 파일에 실제 줄바꿈으로 저장하고 `--body-file`로 전달한다. 저장소와 base·head를 명시한다.
- 생성 응답이 불명확하거나 통신 오류가 나면 열린 PR을 조회해 생성 여부를 확인한 뒤 재시도한다. 같은 실패가 반복되면 원인과 남은 작업을 보고한다.
- 명시적인 요청 없이 merge, force push, 브랜치 삭제 또는 검토자 지정을 하지 않는다.
- 완료 후 PR URL, base·head, 커밋·파일 범위를 확인하고 결과를 보고한다.
