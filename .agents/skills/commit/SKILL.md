# Commit

스테이징된 변경을 하나의 검토 가능한 커밋으로 기록한다.

## 절차

1. `git status --short`와 `git diff --cached --stat`으로 저장소 및 스테이징 상태를 확인한다.
2. `git diff --cached`를 읽고 변경의 목적, 영향 범위와 검증 내용을 파악한다.
3. 서로 무관한 변경이 한 번에 스테이징되어 있으면 커밋하지 않고 분리 필요성을 보고한다.
4. 스테이징된 변경이 없으면 커밋하지 않고 상태를 알린다.
5. 아래 형식으로 메시지를 작성해 `git commit`을 실행한다.
6. 커밋 결과와 커밋 해시를 보고한다.

## 범위 제한

- 스테이징된 파일만 커밋한다.
- 파일을 새로 스테이징하거나 스테이징을 해제하지 않는다.
- 사용자의 명시적인 요청이 없으면 `--amend`, force 옵션과 push를 사용하지 않는다.
- 변경 내용을 확인하지 않은 상태에서 커밋 메시지를 작성하지 않는다.
- 비밀정보, 생성 산출물 또는 의도하지 않은 파일이 포함된 것으로 의심되면 커밋 전에 알린다.

## 메시지 형식

제목은 Conventional Commits 형식을 사용한다.

```text
<type>(<scope>): <summary>
```

`scope`는 모든 커밋 제목에 필수로 작성하며 아래 목록에서 선택한다. 임의의 동의어나 새 scope를 사용하지 않는다. 새 범위가 필요하면 이 목록에 정의한 뒤 사용한다.

| scope | 적용 범위 |
| --- | --- |
| `planning` | 기획 문서: 제품 요구사항, MVP 범위, 역할·일정, 제출용 기획·설명 자료 |
| `design` | 개발 설계 문서: 시스템 구성, AI 파이프라인, 기술 결정·설계 제안 |
| `evaluations` | 테스트·평가 문서: 모델·API 비교, 성능·검증 결과 |
| `meetings` | 회의 문서: 논의, 결정, 액션 아이템 |
| `templates` | 문서·PR 템플릿 |
| `repo` | 저장소 운영: README, 작성·브랜치 규칙, 스킬, 공통 설정 |

파일명이나 디렉터리명 대신 문서의 목적을 기준으로 scope를 선택한다. 여러 영역을 함께 수정하면 변경의 주목적을 기준으로 선택하고, 목적이 다르면 커밋을 나눈다.

여러 파일을 함께 변경할 때는 공통 목적을 나타내는 scope를 선택한다. 서로 무관한 변경을 하나의 scope로 묶지 않는다. 제목은 변경 결과를 나타내는 한국어 명사형 또는 간결한 서술로 작성하고 마침표를 붙이지 않는다.

| 유형 | 사용 기준 |
| --- | --- |
| `feat` | 사용자 또는 시스템에 새 기능을 추가한다. |
| `fix` | 잘못된 동작을 수정한다. |
| `docs` | 문서만 변경한다. |
| `refactor` | 동작을 유지하면서 구조를 변경한다. |
| `test` | 테스트를 추가하거나 수정한다. |
| `perf` | 성능을 개선한다. |
| `build` | 빌드 시스템이나 의존성을 변경한다. |
| `ci` | CI 설정을 변경한다. |
| `chore` | 위 유형에 해당하지 않는 유지보수 작업이다. |

본문은 변경 이유나 제목만으로 드러나지 않는 내용을 설명할 때 작성한다. 파일 목록을 반복하지 않는다. 검증을 수행했다면 실제 실행한 검사만 기록한다.

## 예시

```text
docs(repo): 문서 저장소 운영 기준 추가

- 문서별 책임과 분리 조건 정의
- 향후 문서 디렉터리 생성 기준 명시
```
