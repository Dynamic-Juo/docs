## 기록 시점과 현재 기준

기술 선택 본문과 T-1 ~ T-17은 9월 6일 ~ 9일 당시 구현·실험을 설명한다. 현재 구현 상태는 [9월 13일 재점검](mvp-implementation-audit.md#2026-09-13-재점검)을 우선한다. 당시 측정값은 모델·영상·실행 경로가 다른 최신 배포 성능으로 일반화하지 않는다.

PR #4의 45초는 자막 경로의 전체 처리 기록이며 23분 발언 전체의 STT 시간이 아니다. 한국어 STT의 53 ~ 89초 역시 해당 실험 조건에서만 읽는다. [정정 답변](https://github.com/chamsae-ai/docs/pull/4#discussion_r3970133929)을 반영한다. 프레임 분류 점수는 보정된 실제 합성 확률로 해석하지 않는다.

9월 13일 코드에서는 자막 기본값 `off`, 집계 `trimmed_mean`, LLM 추출 실패의 명시적 분석 불가 처리가 적용됐다. 아래의 수동 자막 기본값·blend·LLM 실패 시 규칙 대체는 이전 구현 설명이다. 전문 기관 rating을 원문 검증 없이 옮기던 경로도 현재 판정 기준이 아니다.

## 이 문서의 목적

팀장이 설계한 파이프라인(`design/ai-pipeline.md`)을 구현하면서 **어떤 문제 때문에 이 모델·라이브러리를 골랐고, 그래서 무엇이 좋아졌으며, 무엇이 여전히 한계인지**를 남긴다. 아래 "테스트 기록"은 실행할 때마다 계속 덧붙이는 누적 로그다. 새로 알게 된 것이 생기면 맨 아래에 날짜와 함께 추가한다.

각 선택의 근거는 실제로 돌려본 결과로만 적는다. 재보지 않은 것은 "미측정"이라고 쓴다.

**[테스트 기록](#테스트-기록)은 이 문서 아래쪽에 있다.** 본문에서 `테스트 기록 T-4` 같은 참조가 나오면 그쪽을 보면 된다.

## 1. 영상·음성·자막 수집 — yt-dlp

**해결한 문제.** 파이프라인의 모든 단계가 원본 미디어를 필요로 하는데, YouTube는 화면과 소리를 별도 스트림(DASH)으로 내보내고 자막은 또 다른 경로에 있다. 세 가지를 각각 받아야 한다.

**왜 이것인가.** 영상·오디오·자막을 한 도구로 받고, 포맷 선택 문법으로 "해상도 상한을 둔 영상"과 "오디오만"을 따로 지정할 수 있다. 메타데이터(제목·설명·업로더·길이·언어)도 같은 호출에서 나와서 자가표기 판정에 바로 쓸 수 있다.

**얻은 이점.** 다운로드 단계 하나로 이후 세 단계(프레임 분석·음성 인식·자가표기 확인)의 입력이 전부 채워진다. 자막이 있으면 음성 인식을 통째로 건너뛸 수 있는데, 실측에서 이 차이가 가장 컸다(테스트 기록 T-3 참조).

**한계.** YouTube 쪽 변경에 취약해 버전 고정이 필요하다. 이용 조건·라이선스는 아직 확인하지 않았다(MVP T-13).

## 2. 음성 인식 — faster-whisper (CTranslate2)

**해결한 문제.** 자막이 없는 영상에서 발언 텍스트를 얻어야 한다. 주장 추출의 입력이 여기서 나오므로, 여기서 틀리면 뒤 단계가 전부 무의미해진다.

**왜 이것인가.** OpenAI Whisper 원본 대비 CTranslate2 런타임으로 재구현한 버전이라 CPU에서 int8 양자화로 돌릴 수 있다. 배포 대상이 GPU 없는 환경(맥미니 도커, 혹은 ARM 클라우드)이라 CPU 성능이 실질적인 제약이었다. Apple Silicon의 MPS 가속은 이 스택에서 지원되지 않아 어차피 CPU다.

**얻은 이점.** GPU 없이도 3분급 영상을 1분 안팎에 처리한다. 모델 크기를 설정값(`DEEPCHECK_WHISPER_MODEL_SIZE`)으로 바꿀 수 있어 속도·품질을 배포 환경에 맞춰 조절한다. 한국어 인식 품질이 YouTube 자동 자막보다 눈에 띄게 좋다(테스트 기록 T-4).

**한계.** 한국어 고유명사와 숫자 단위에서 여전히 틀린다. 특히 조·억 단위 수치를 잘못 듣는 사례가 실제로 나왔고, 이건 팩트체크에 직결되는 위험이다(테스트 기록 T-5).

## 3. 자막 우선 정책 — 사람이 단 자막만 사용

**해결한 문제.** 자막이 있으면 음성 인식을 건너뛸 수 있어 속도가 크게 는다. 그런데 YouTube 자동 자막도 "자막"으로 잡힌다.

**왜 이렇게 했는가.** 자동 자막은 결국 다른 STT의 출력이고, 실측해보니 우리 faster-whisper보다 품질이 낮았다. 그래서 기본값은 `manual`(사람이 단 자막만)로 두고, `any`(자동 자막까지)·`off`(항상 STT)를 설정으로 열어뒀다.

**얻은 이점.** 품질을 지키면서도 좋은 자막이 있는 영상에서는 음성 인식 시간을 0초로 만든다. 기본값을 바꾸지 않고 환경변수만으로 비교 실험을 할 수 있다.

**한계.** 한국어 뉴스 콘텐츠에는 사람이 단 자막이 거의 없어서, 실제로는 대부분 STT 경로를 탄다.

**팀 결정 대기.** MVP 확정 문서의 T-02는 "MVP 분석은 자막을 사용하지 않고 음성 인식으로 발언 텍스트를 확보한다"로 되어 있어 현재 구현과 어긋난다. 실측 기준으로 자막이 있으면 0초, 없으면 53~89초라 M-07의 "첫 결과 1분"에 직결되는 항목이다. PR 리뷰에서 판단을 요청했다.

## 4. 얼굴 검출·crop — MediaPipe BlazeFace

**해결한 문제.** 프레임 전체를 딥페이크 분류기에 넣으면 배경·자막·로고가 입력의 대부분을 차지한다. 분류기는 얼굴을 보도록 학습됐으므로 얼굴 영역만 잘라 넣어야 한다.

**왜 이것인가.** CPU에서 가볍고, 추가 모델 다운로드 없이 패키지에 포함돼 있으며, 얼굴이 없을 때 "없음"을 명확히 반환한다. 이 마지막 성질이 중요한데, 얼굴을 못 찾은 것을 "정상 영상"으로 처리하지 않고 `분석 불가`로 응답하는 규칙(`ai-pipeline.md`)을 지키려면 검출 실패를 신호로 받아야 하기 때문이다.

**얻은 이점.** 분류기 입력이 얼굴로 좁혀지면서 프레임 점수의 분산이 줄었다. 얼굴 없는 영상에서는 정직하게 판단을 유보한다.

**한계.** 현재 프레임당 가장 큰 얼굴 하나만 쓴다. 여러 사람이 나오는 영상의 처리 기준은 정하지 않았다(MVP T-05).

## 5. 딥페이크 분류 — `dima806/deepfake_vs_real_image_detection` (ViT)

선정 과정과 후보 비교는 [딥페이크 탐지 모델 비교](deepfake-detection-model-comparison.md)에 따로 적었다. 요약하면, CPU 추론이 가능하고 얼굴 crop 입력을 전제로 학습된 공개 모델 중 접근성과 응답 시간이 현실적인 것을 골랐다.

**추가로 한 것: 프레임 점수 집계 방식.** 단순 평균은 강한 단일 프레임 신호를 희석시킨다. 8프레임 중 1장이 98.4% fake인데 평균이 13/100까지 떨어지는 사례를 실제로 만났다. 그래서 평균과 최댓값을 0.6:0.4로 섞는다. 이 가중치는 실측으로 튜닝해야 할 판단값이지 검증된 최적값이 아니며, 설정으로 조절 가능하다.

9월 10일 후속 [절사평균 비교 기록](frame-aggregation-comparison.md)에서 두 영상과 프레임 수별 결과를 확인했다. 현재 기본값은 trimmed_mean이며 소수 표본 비교와 일반화 검증은 구분한다.

## 6. 프레임 추출 — PyAV

**해결한 문제.** 컨테이너에 시스템 ffmpeg 바이너리를 넣지 않기로 했는데(이미지 크기), 프레임은 뽑아야 한다.

**왜 이것인가.** PyAV는 ffmpeg 라이브러리를 파이썬 패키지 안에 품고 있어 별도 설치 없이 디코딩이 된다. 서브프로세스가 아니라 라이브러리 호출이라 타임아웃·오류 처리도 예외로 잡힌다.

**얻은 이점.** 이미지가 작아지고, 프레임 추출 실패가 프로세스 종료가 아니라 단계 실패로 격리된다.

## 7. 주장 추출 — 규칙 기반과 LLM 두 가지

**해결한 문제.** 3분 영상의 발언 전체가 팩트체크 대상은 아니다. "검증 가능한 사실 주장"만 골라야 한다.

**왜 규칙 기반부터 만들었나.** 처음부터 LLM을 넣으면 비용·지연·키 발급이 전부 변수가 되어 어디가 진짜 병목인지 알 수 없다. 규칙 기반으로 파이프라인 전체를 끝까지 돌려서 확인하는 편이 낫다고 판단했다. **그 답이 나왔고, 병목은 추출이 아니라 판정이었다**(테스트 기록 T-13).

**규칙 기반이 고르는 방식.** 문장을 나눈 뒤 각 문장에 점수를 준다 — 백분율 +3, 수량 표현 +2, 연도 +2, 숫자 +1, 고유명사 +1. 합이 2 이상이고 단정형 종결(`니다`/`습니다` 등)이면 후보로 삼고, 미래 전망 표현은 제외한다.

외부 의존 없이 즉시 동작하고 왜 뽑혔는지 로그로 설명되지만, 두 가지를 구조적으로 못 잡는다. **수치 없는 사실 주장**과 **대명사로 앞을 가리키는 주장**이다. 종결어미를 아무리 보강해도 후자는 안 된다 — 문장 하나만 보기 때문이다(테스트 기록 T-6).

**LLM 추출을 붙인 이유.** 위 두 가지를 잡고, M-04가 요구한 "같은 의미 주장 병합"도 처리하기 위해서다. 실측에서 같은 영상 기준 규칙 5건 → LLM 8건으로 늘었다(테스트 기록 T-14).

**안전장치.** LLM이 뽑은 문장이 발언 전문에 실제로 있는지 대조하고, 없으면 버린다. 발언하지 않은 문장을 검증 대상에 올리면 그 자체가 허위 정보이기 때문이다. 대명사가 가리키는 대상은 별도 필드에 적게 하고 **주장 문장 자체는 원문 그대로 둔다** — 다시 쓰게 하면 원문 대조를 통과할 수 없다.

**얻은 이점.** `DEEPCHECK_CLAIM_EXTRACTOR`로 둘을 바꿔 끼울 수 있고, LLM이 실패하면 규칙으로 떨어진다. 데모 당일 외부 API가 죽어도 최소한 규칙 수준은 나온다.

**한계.** LLM 추출은 호출 비용과 지연이 붙는다(실측 약 3초). 규칙 기반은 여전히 문체에 취약하다.

## 8. 근거 검색 — 전문 기관 판정 + 네이버 + 위키백과

**해결한 문제.** 판정할 재료를 모아야 한다. 여기가 비면 판정기가 아무리 좋아도 결과는 전부 `근거 부족`이다.

**조회 순서.** 전문 기관 판정(Google Fact Check Tools) → NAVER API HUB 검색(뉴스·백과사전) → 위키백과 한국어·영어. 주장의 핵심어가 근거 제목·인용문에 없으면 버리는 관련성 필터를 통과한 것만 카드에 붙인다.

**왜 네이버를 넣었나.** 우리가 뽑는 주장은 대부분 한국 뉴스의 수치·정책 발언인데, **그건 백과사전에 없고 기사에 있다.** 위키백과만 쓸 때는 물가 주장에 "박정희", "T-50 골든이글" 같은 문서가 붙었다. 관련성 필터를 통과할 만큼 낱말은 겹치지만 판정에는 아무 쓸모가 없는 자료다.

블로그·카페·지식iN 카테고리는 신청하지 않았다. 개인 게시물을 판정 근거로 붙이면 결과가 오염되고, `evidence-policy.md`의 출처 선택 기준에도 맞지 않는다. 코드에서도 해당 카테고리는 provider를 만들지 않는다.

**얻은 이점.** 근거에 **출처 유형**(통계 원문 / 공식 발표 / 팩트체크 판정 / 언론 보도 / 백과사전)을 붙였다. `evidence-policy.md`가 "1차 출처를 우선하고 없으면 독립 출처 두 개 이상"을 요구하는데, 그 규칙을 적용하려면 유형을 알아야 한다.

**한계.** Google Fact Check API 키는 아직 발급되지 않았다. 다만 그 API는 이미 누군가 팩트체크한 주장만 색인하므로, 어제 올라온 쇼츠 발언에는 구조적으로 잘 걸리지 않는다. 나머지 대안은 [팩트체크 방법론 대안](factcheck-method-options.md)에 정리했다.

## 8-1. 판정 — LLM + 인용 검증

**해결한 문제.** 근거를 모아도 "이 근거가 주장과 맞는가"를 판단할 수단이 없었다. 그래서 **모든 주장이 판단 유보로 끝났다**(테스트 기록 T-13).

**판정 사다리.** 신뢰도 순으로 시도한다.

1. 전문 기관의 공개 판정이 있으면 그대로 옮긴다 — 우리 추론보다 신뢰도가 높다
2. 없으면 LLM에게 근거를 주고 관계를 판정하게 한다
3. LLM도 못 쓰면 근거만 붙이고 유보한다

**LLM을 선택한 이유.** 주장 요소 비교와 한국어 판정 사유를 하나의 구조화된 응답으로 다루기 위해 사용했다. NLI는 함의·모순·중립을 분류하는 작업이며 분류 모델도 잘못 판단할 수 있다. LLM과 NLI를 생성·분류라는 이유만으로 안전성 순위로 나누지 않는다. NLI 추가 여부는 후속 검증 과제다.

**인용 검증의 범위.** LLM을 판정에 넣으면 근거가 부실해도 그럴듯한 판정을 만들어낼 위험이 생긴다. 허위 정보를 다루는 서비스가 그러면 우리가 막으려던 것과 같은 일을 하게 된다.

그래서 LLM에게 판정과 함께 **모델에 전달한 근거 텍스트에서 그대로 발췌한 문장**을 제출하게 하고, 그 문장이 실제 근거에 있는지 서버가 문자열로 대조한다. 없으면 판정을 통째로 버리고 `근거 부족`으로 강등한다. 이 검사는 존재하지 않는 인용을 걸러내지만, 인용과 주장의 의미 관계가 맞다는 보장은 아니다. 당시 검색 발췌 대조와 현재 원문·출처 검증 조건을 구분한다.

**얻은 이점.** 판정과 함께 이유가 나오고(U-02), 근거 부족 사유를 7종으로 구분한다(U-03). 특히 시점 불일치를 잡는다 — 2022년 발언을 2019년 자료와 대조해 수치가 다르다는 이유로 불일치를 내면 틀린 판정인데, 그걸 구분한다(테스트 기록 T-13).

**한계.** 외부 API 호출이라 지연과 비용이 붙는다. 제공자를 설정으로 교체할 수 있게 만들어서(`DEEPCHECK_LLM_PROVIDER`), 운영에서 비용이 문제가 되면 호스트 Ollama로 옮길 수 있다. `off`로 두면 전부 규칙 기반으로 동작한다.

## 9. 실행 구조 — FastAPI + 작업 큐 폴링

**해결한 문제.** 3분 영상 분석에 수십 초에서 수 분이 걸린다. HTTP 요청 하나로 끝까지 기다리면 타임아웃·재시도·중복 실행이 전부 문제가 된다.

**왜 이렇게 했는가.** 분석 요청은 `jobId`만 즉시 돌려주고, 프런트가 폴링한다. 워커는 스레드 풀로 제한해 동시 실행 수를 통제한다.

**얻은 이점.** UI가 진행 단계를 실시간으로 보여줄 수 있고, 서버는 부하를 큐로 흡수한다. 같은 URL이 동시에 들어오면 진행 중인 작업을 재사용한다.

**추가로 한 것: 점진적 결과 전달.** 주장 개수가 확정되는 즉시 카드를 전부 대기 상태로 내보내고, 검증되는 대로 하나씩 갱신한다. 미디어 조작 결과는 주장 검증을 기다리지 않고 먼저 나간다. 실측 폴링에서 4초에 빈 결과, 40초에 두 축과 카드 혼재, 44초에 전체 완료를 확인했다.

**추가로 한 것: 로그 상관관계.** `contextvars`로 `job_id`와 `request_id`를 로그 레코드에 실었다. 워커 3개가 동시에 돌아도 어느 작업의 로그인지 구분된다. 이건 나중에 운영하면서 마이그레이션할 때를 대비한 것이다.

## 10. 배포 — 도커 (CPU 전용 파이토치)

**해결한 문제.** 기본 PyPI의 torch를 그대로 설치하면 CUDA 관련 패키지가 약 2GB 딸려 들어온다. GPU가 없는 배포 대상에서는 전부 낭비다.

**왜 이렇게 했는가.** CPU 전용 wheel 인덱스에서 torch를 먼저 설치한 뒤 나머지 요구사항을 설치한다.

**얻은 이점.** 이미지 1.89GB(arm64), 컨테이너 실행 메모리 1.08GB. 헬스체크와 로그 로테이션을 붙였고, 설정은 선택적 `.env`로 주입한다.

**한계.** AWS 프리티어 인스턴스로는 메모리가 부족하다. 오라클 ARM 프리티어나 맥미니 자체 배포는 가능하다.

# 테스트 기록

실행하면서 알게 된 것을 시간순으로 쌓는다. 새 발견은 아래에 계속 덧붙인다.

## T-1. 프레임 추출 실패가 "정상 영상"으로 둔갑했다 (2026-09-06)

**무엇을 했나.** 프레임이 0장 추출되는 상황을 만들어 응답을 확인.

**무엇을 발견했나.** 프레임이 0장이면 평균 fake 점수가 0.0이 되고, 그대로 "진짜일 가능성 높음"으로 응답했다. 분류기 로드 실패와 음성 인식 실패도 같은 방식으로 조용히 낮은 위험도로 강등됐다.

**왜 문제인가.** `ai-pipeline.md`가 명시한 "얼굴을 찾지 못한 것을 정상 영상 판정으로 처리하지 않는다"에 정면으로 어긋난다. 사용자에게는 "안전함"으로 보이지만 실제로는 아무것도 검사하지 못한 상태다.

**어떻게 했나.** 분석이 불가능했으면 위험도를 `null`, 상태를 `분석 불가`로 응답하도록 바꾸고, 이 경로를 회귀 테스트로 고정했다.

## T-2. 컨테이너에서 얼굴 검출이 한 번도 동작하지 않았다 (2026-09-06)

**무엇을 했나.** 도커에서 실제 영상을 돌리고 얼굴 검출 로그를 확인.

**무엇을 발견했나.** 6프레임 중 0장에서 얼굴을 찾았다. 로컬에서는 잘 되던 것이 컨테이너에서만 실패했다. 원인은 `libEGL.so.1` 부재로 MediaPipe 검출기가 아예 로드되지 않은 것이었다. 그런데 코드는 이걸 "얼굴 없음"과 구분하지 못했다.

**어떻게 했나.** 이미지에 `libgl1 libegl1 libgles2 libglib2.0-0`을 추가. 같은 영상에서 6프레임 중 5장 검출로 바뀌었다.

**교훈.** 로컬에서 되는 것과 컨테이너에서 되는 것은 다르다. 그리고 **로드 실패와 검출 결과 없음을 로그에서 구분할 수 있어야 한다** — 이 사건 전에는 두 경우가 같은 로그를 남겼다.

## T-3. 자막이 있으면 음성 인식 시간이 0초가 된다 (2026-09-07)

**무엇을 했나.** 사람이 단 자막이 있는 영상과 없는 영상의 단계별 소요 시간 비교.

**측정값.**

| 경로 | 발언 텍스트 확보 소요 |
| --- | --- |
| 사람이 단 자막 사용 (2223단어) | 0.0초 |
| 한국어 STT, `small` | 88.6초 |
| 한국어 STT, `tiny` | 53.1초 |

같은 영상의 다른 실행에서 `small` 52.0초도 기록됐다. 영상 길이와 CPU 상태에 따라 편차가 크다.

**의미.** 자막 유무가 전체 응답 시간을 좌우하는 가장 큰 변수다. MVP의 "첫 결과 1분" 목표는 자막이 없는 한국어 영상에서 빠듯하다.

## T-4. YouTube 자동 자막은 우리 STT보다 나쁘다 (2026-09-07)

**무엇을 했나.** 한국어 뉴스 영상(YTN 추석 물가)에서 자동 자막 경로와 faster-whisper `small` 경로의 출력을 나란히 비교.

**무엇을 발견했나.**

| 실제 발언 | 자동 자막 | faster-whisper `small` |
| --- | --- | --- |
| 소고기, 명태 | 쏘고 김형태 드 | 소고기, 명태 |
| 농축수산물 할인 쿠폰 | 동축 쌈을 할인쿠폰 | 농축 수산물 할인 쿠폰 |
| 소상공인과 중소기업 | 포상 고인과 중 소비 업 | 소상공인과 중소기업 |

**어떻게 했나.** 자막 정책 기본값을 `manual`(사람이 단 자막만)로 확정했다. 자동 자막은 설정으로 켤 수 있게만 두고 기본 경로에서 뺐다.

## T-5. 두 STT가 같은 숫자를 다르게 들었다 — 팩트체크 직결 위험 (2026-09-07)

**무엇을 했나.** T-4와 같은 영상에서 뽑힌 주장 문장을 비교.

**무엇을 발견했나.** 같은 발언에 대해

- 자동 자막: "4 12조원 규모의 명절 대처 고증 자금"
- faster-whisper: "42조 원 규모의 명절 대출 보증자금"

**왜 심각한가.** 숫자 하나가 10배 차이 난다. 주장 추출이 수치를 우선하도록 설계돼 있으므로, 이런 문장은 **반드시** 팩트체크 대상으로 올라간다. 발언 텍스트가 틀리면 팩트체크는 존재하지 않는 주장을 검증하게 되고, 결과가 맞든 틀리든 무의미하다.

**함의.** 팩트체크 정확도의 상한은 STT 정확도가 정한다. 근거 검색을 아무리 개선해도 이 단계를 넘지 못한다. 향후 판정 결과를 신뢰도와 함께 보여줄 때, "발언 인식 신뢰도"를 별도 축으로 노출하는 것을 검토해야 한다.

## T-6. 한국어 뉴스체 종결어미를 놓쳐 주장을 못 뽑았다 (2026-09-07)

**무엇을 했나.** 사실 주장이 8건 들어 있는 한국어 뉴스 영상으로 주장 추출을 실행.

**무엇을 발견했나.** 1건만 추출됐다. 종결어미를 열거식으로 매칭하고 있었는데 뉴스체 문장 대부분이 목록에 없었다. 이후 구어체를 보강한 뒤에도 `-는데요`를 놓쳐 5건이어야 할 것이 4건으로 나왔다.

**어떻게 했나.** 문장 끝 단정형을 폭넓게 인식하도록 바꾸고 구어체 종결어미를 추가했다.

**교훈.** 한국어 주장 추출에서 종결어미 열거는 계속 새는 방식이다. 규칙 기반을 유지하는 한 문체가 바뀔 때마다 같은 문제가 반복된다. T-07(주장 추출 모델) 결정 시 이 비용을 고려해야 한다.

## T-7. 관련 없는 근거가 붙었다 (2026-09-07)

**무엇을 했나.** 물가 관련 주장의 근거 목록을 확인.

**무엇을 발견했나.** "주기율표", "동일본 대진재" 같은 문서가 근거로 붙었다. 검색어에서 의미 없는 토큰이 매칭된 결과였다.

**어떻게 했나.** 주장의 핵심어가 근거 제목이나 인용문에 실제로 등장하는지 확인하는 관련성 필터를 넣었다.

**남은 문제.** 필터는 "관련 없는 것을 뺀다"까지만 한다. 통과한 근거가 주장을 지지하는지 반박하는지는 여전히 판단하지 못한다.

## T-8. 소수점이 포함된 수치가 쪼개졌다 (2026-09-07)

**무엇을 했나.** 핵심어 추출 결과 확인.

**무엇을 발견했나.** "6.0%"가 마침표를 문장 구분자로 취급당해 "0%"가 됐다. 검색어 자체가 틀린 채로 근거를 찾고 있었다.

**어떻게 했나.** 숫자 사이의 마침표는 보존하고 그 외 마침표만 공백으로 바꾸도록 수정.

## T-9. YouTube 롤링 자막이 세 번씩 중복됐다 (2026-09-07)

**무엇을 했나.** 자막 파싱 결과의 단어 수를 원본과 대조.

**무엇을 발견했나.** YouTube의 한 줄씩 밀려 올라가는 자막 형식 때문에 같은 문장이 여러 번 들어갔다. 단어 수가 실제의 두세 배로 부풀었고, 그만큼 주장 추출의 구간 분산도 왜곡됐다.

**어떻게 했나.** 앞 자막과 단어 앞부분을 비교해 겹치는 만큼 잘라내는 방식으로 중복을 제거.

## T-10. 분석 상태가 항상 "부분 완료"로 나왔다 (2026-09-07)

**무엇을 했나.** 모든 단계가 정상인 영상의 최종 상태 확인.

**무엇을 발견했나.** 주장 검증 옵션이 꺼져 있어 `skipped`인 것을, 상태 판정 로직이 "실패한 단계"로 세고 있었다. 그래서 완전 정상인 결과도 부분 완료로 응답했다.

**어떻게 했나.** 상태 판정에서 해당 단계를 제외.

**교훈.** `skipped`(의도적으로 안 함)와 `failed`(하려다 실패)는 다른 것이고, 상태 집계에서 섞이면 안 된다.

## T-11. 점진적 결과 전달 실측 (2026-09-07)

**무엇을 했나.** 실제 API에 요청을 넣고 폴링하면서 매 시점의 결과 키를 기록.

**측정값.**

| 경과 | 응답에 들어 있던 것 |
| --- | --- |
| 4초 | 빈 결과, 상태 `processing:collecting` |
| 40초 | 미디어 조작 두 축 완료, 주장 카드 5장(일부 대기·일부 완료) |
| 44초 | 전체 완료 |

**의미.** U-01(순차 제공)이 실제로 동작한다. 다만 첫 결과가 40초에 나온 것은 자막이 있는 짧은 영상 기준이며, 자막 없는 한국어 영상에서는 STT 시간만큼 밀린다.

## T-12. 주장 검증 소요 시간 (2026-09-07)

**측정값.** 주장 5건 검증에 9.45초. 근거 제공자별로는 GDELT가 16.8초에 429 응답까지 나와 기본 제공자에서 제외했다.

**단계별 실측 예시(짧은 영어 영상).** 다운로드 10.9초 / 프레임 추출 4.1초 / 미디어 조작 분석 1.5초 / 자막 0.0초 / 주장 검증 3.3초.

## T-13. 판정 단계를 넣기 전까지는 모든 주장이 판단 유보였다 (2026-09-09)

**무엇을 했나.** 근거를 읽고 판정하는 단계를 파이프라인에 넣고 실제 영상으로 확인.

**그 전 상태.** 우리가 `지지`/`반박`을 낼 수 있는 유일한 경로가 전문 기관의 공개 판정 표기였는데, 그 API 키가 없어서 **모든 주장이 100% 판단 유보**로 끝났다. 근거는 모아 보여주지만 판정이 없는 상태였다.

**어떻게 했나.** 판정을 신뢰도 순으로 시도하도록 바꿨다.

1. 전문 기관의 공개 판정이 있으면 그대로 옮긴다
2. 없으면 LLM에게 근거를 주고 관계를 판정하게 한다
3. LLM도 못 쓰면 근거만 붙이고 유보한다

**격리 테스트 결과(DeepSeek).**

| 상황 | 판정 | 모델이 쓴 이유 |
| --- | --- | --- |
| 근거가 주장을 뒷받침 | 근거와 일치 | "근거가 8월 소비자물가 상승률이 외환위기 이후 최고치라고 직접 밝히고 있어 주장과 일치한다" |
| 근거의 수치가 다름(6.3% vs 주장 12%) | 근거와 불일치 | "근거는 6.3%라고 명시하여 주장의 12%와 다릅니다" |
| 근거의 시점이 다름(2019년 자료 / 2022년 주장) | 근거 부족 | "2019년 수치만 언급하며 2022년 8월을 다루지 않아 확인할 수 없다" |

세 번째가 중요하다. **수치가 다른데도 불일치로 단정하지 않고 시점 문제를 짚었다.** evidence-policy.md가 요구한 동작이다.

## T-14. LLM 주장 추출이 규칙보다 더 뽑는다 (2026-09-09)

**무엇을 했나.** 같은 한국어 뉴스 영상에서 규칙 기반과 LLM 기반 추출을 비교.

**측정값.** 규칙 5건 → LLM 8건.

규칙이 놓치던 것은 **수치가 없는 사실 주장**이었다. 예: "정부가 오늘 윤석열 대통령 주재로 비상경제 민생회의를 열고 추석 민생 안정 대책을 논의했다." 검증 가능한 사실인데 점수 기준(백분율·수량·연도)에 걸리지 않아 후보에서 빠졌다.

**안전장치.** LLM이 뽑은 문장이 발언 전문에 실제로 있는지 대조하고, 없으면 버린다. 발언하지 않은 문장을 검증 대상에 올리면 그 자체가 허위 정보이기 때문이다. 이 실행에서는 제외 0건이었다.

## T-15. 수량 정규식에 조·경 단위가 빠져 있었다 (2026-09-09)

**무엇을 발견했나.** "42조원 규모의 명절 대출 보증자금을 공급합니다"가 주장 후보에서 탈락하고 있었다. 수량 패턴이 `명|원|달러|억|만|천|배…`만 인식해서 "42조"의 "조"를 못 잡았고, 숫자 점수 1점으로 임계값(2점) 미달이었다.

**왜 중요한가.** 뉴스에서 가장 흔한 수치 표현이고, 하필 테스트 기록 T-5에서 두 STT가 서로 다르게 들었던(42조 vs 4.12조) 바로 그 문장이다. 팩트체크가 가장 필요한 주장이 조용히 빠지고 있었다.

**교훈.** 규칙 기반 추출은 이런 식으로 샌다. 어떤 단위가 빠졌는지는 실제 영상을 돌려봐야만 드러난다.

## T-16. 병렬 처리가 만든 회귀 두 가지 (2026-09-09)

주장 검증을 3건 병렬로 바꾼 뒤(M-07) 실제 영상에서 두 가지가 깨졌다. 둘 다 단위 테스트를 통과한 상태에서 컨테이너에서만 드러났다.

**① 근거가 통째로 비었다.** 같은 호스트로 동시 요청이 나가면서 위키백과가 429(속도 제한)를 돌려줬다. 병렬은 유지하되 호스트 단위로만 요청을 줄 세우고 429에 백오프 재시도를 붙여 해결했다. Wikimedia는 연락처가 없는 User-Agent를 더 강하게 제한하는데 우리 값에 연락처가 없던 것도 함께 고쳤다.

**② 로그에서 job_id가 사라졌다.** contextvar가 새 스레드로 전파되지 않아 병렬 구간의 로그가 전부 `job:-`로 남았다. 워커가 여러 개 도는 서버에서는 어느 작업의 로그인지 알 수 없어 사실상 디버깅이 불가능하다.

고치려고 `contextvars.copy_context()`를 스레드에 넘겼는데 **그게 더 나빴다.** Context 객체 하나에 두 스레드가 동시에 진입할 수 없어서 `cannot enter context ... is already entered`로 터졌고, 컨테이너에서 분석이 통째로 실패했다. 값만 캡처해 각 스레드가 자기 컨텍스트에 다시 심는 방식으로 바꿨다.

**테스트가 이 버그를 놓쳤다.** 스레드가 실제로 겹치지 않고 순차로 끝나버려서 통과했기 때문이다. Barrier로 동시 진입을 강제하도록 고치고, 고치기 전 코드에서 실패하는 것을 확인했다. **동시성 테스트는 동시성을 강제해야 한다** — 병렬로 실행한다는 사실만으로는 겹침이 보장되지 않는다.

## T-17. 네이버 검색 API가 이관됐다 (2026-09-09)

**무엇을 발견했나.** 기존 개발자센터의 검색 API가 2026년 7월 31일에 종료되고 네이버 클라우드의 NAVER API HUB로 이관됐다. 도메인·경로·인증 헤더가 모두 바뀌어서 도메인만 갈아끼워서는 동작하지 않는다.

| | 종료된 방식 | 현재 |
| --- | --- | --- |
| 도메인 | `openapi.naver.com` | `naverapihub.apigw.ntruss.com` |
| 경로 | `/v1/search/news.json` | `/search/v1/news` |
| 인증 헤더 | `X-Naver-Client-Id` | `X-NCP-APIGW-API-KEY-ID` |

**왜 위험한가.** 규격이 어긋나면 401만 나고 근거가 조용히 비기만 한다. 파이프라인은 정상 종료되고 결과도 나오는데 판정만 안 될 뿐이라, 원인을 찾기 어렵다. 호출 URL과 헤더를 테스트로 고정했다.

**요금은 문제없다.** 월 775,000건까지 무료, 일 최대 25,000건이다. 영상 한 편에 약 16회(주장 8건 × 카테고리 2개)를 쓰므로 하루 1,500편까지 가능하다.
