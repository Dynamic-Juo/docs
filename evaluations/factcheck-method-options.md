# 팩트체크 방법론 대안 검토 — Google Fact Check API 외에

- 작성자: 나정균 팀원
- 작성일: 2026-09-08
- 관련 MVP 항목: T-08(한국어 근거 검색 수단), T-09(검색 순서), T-10(근거 선택·비교), T-11(판정 모델)

## 왜 이 검토가 필요한가

현재 파이프라인의 판정 규칙은 **전문 기관이 공개한 판정 표기가 있을 때만 `지지`/`반박`을 낸다.** 근거를 읽고 스스로 판정하는 단계가 없기 때문에, 없는 능력을 있는 척하지 않기로 한 선택이다.

문제는 그 전문 기관 판정을 가져올 유일한 경로인 Google Fact Check Tools API 키가 아직 발급되지 않았다는 것이다. 지금 실제로 동작하는 근거 제공자는 위키백과뿐이고, 위키백과 문서는 판정 근거가 아니라 참고 자료다. **그래서 현재 모든 주장이 `판단 유보`로 끝난다.**

키가 발급되더라도 남는 문제가 있다. Google Fact Check Tools가 색인하는 것은 **이미 누군가 팩트체크한 주장**뿐이다. 우리가 다루는 것은 어제 올라온 쇼츠의 발언이고, 그건 대개 아직 아무도 검증하지 않았다. 즉 이 경로만으로는 적중률이 구조적으로 낮다.

아래는 대안들이다. **접근 조건을 직접 확인하지 못한 것은 그렇게 표시했다.** 실제 채택 전에 신청·조회를 해봐야 한다.

## 판정 구조를 먼저 정리하면

대안을 나열하기 전에 짚을 게 있다. 팩트체크는 두 가지가 필요한데 지금 우리는 첫 번째만 있다.

1. **근거를 찾는다** (검색) — 지금 있음, 위키백과
2. **근거와 주장을 비교해 판정한다** (추론) — 지금 없음

아래 대안은 이 둘 중 어느 쪽을 채우는지에 따라 성격이 다르다. 섞어서 보면 판단이 흐려지므로 나눠서 적는다.

# A. 근거를 찾는 수단

## A-1. 한국언론진흥재단 BigKinds 뉴스 API

**무엇인가.** 한국언론진흥재단이 운영하는 뉴스 빅데이터 분석 서비스. 국내 언론사 기사 본문을 대상으로 검색·연관어 분석 등을 API로 제공한다.

**우리 파이프라인에 왜 맞는가.** 우리가 뽑는 주장은 대부분 한국 뉴스에서 나온 수치·정책 발언이다. 위키백과에는 "2022년 8월 추석 성수품 할인 쿠폰 650억 원" 같은 건 없지만, 뉴스 기사에는 있다. 우리 관련성 필터가 요구하는 "핵심어가 근거 본문에 실제로 등장하는가"를 뉴스 본문이 가장 잘 만족한다.

**이점.** 발언 시점 근처의 기사를 찾을 수 있어 T-10의 "발표 시점 적합성"을 다룰 근거가 생긴다. 기사 발행일이 명확해 근거 카드에 그대로 붙일 수 있다.

**한계와 확인할 것.** 검색 결과에 따르면 신청 절차 없이 전 국민에게 제공된다는 안내가 있으나, 실제 API 키 발급 방식·호출 제한·상업적 이용 조건은 직접 확인해야 한다. 그리고 **뉴스 기사는 판정이 아니라 자료다.** 기사가 나왔다는 사실이 주장이 참이라는 뜻은 아니다(언론이 발언을 그대로 인용한 기사일 수 있다). 이 구분을 UI에서 흐리면 안 된다.

**우선순위: 높음.** 한국어 시사 콘텐츠라는 우리 범위에 가장 잘 맞고, 접근 장벽이 낮아 보인다.

## A-2. 네이버 검색 API (뉴스·백과사전)

**무엇인가.** 네이버 개발자센터에서 발급하는 검색 API. 뉴스·백과사전·블로그 등 카테고리별 검색을 제공한다.

**이점.** 발급이 간단하고 응답이 빠르다. 한국어 검색 품질이 좋다. 위키백과가 못 덮는 시사 영역을 보완한다.

**한계와 확인할 것.** 일일 호출 한도와 상업적 이용 조건 확인 필요. 검색 결과가 제목·요약 수준이라 본문 대조가 어렵다. 블로그·카페 결과가 섞이면 신뢰도가 낮은 자료를 근거로 붙이게 되므로 카테고리를 제한해야 한다.

**우선순위: 높음.** 실험 비용이 가장 낮다. BigKinds 신청이 오래 걸리면 먼저 붙여볼 것.

## A-3. 통계 원본 직접 조회 — KOSIS, 공공데이터포털

**무엇인가.** 국가통계포털(KOSIS)과 공공데이터포털이 제공하는 통계 조회 API.

**왜 이게 특히 우리에게 맞는가.** 우리 주장 추출은 **수치를 우선하도록 설계돼 있다** — 백분율 +3, 수량 +2, 연도 +2 점수를 준다. 즉 파이프라인이 골라내는 주장 대부분이 "소비자물가 상승률이 6%다", "성수품 공급을 1.4배로 늘린다" 같은 **숫자 주장**이다. 이런 건 기사를 읽고 해석할 필요 없이 통계 원본과 직접 대조할 수 있다.

**이점.** 이게 유일하게 **진짜 판정을 만들어낼 수 있는 경로**다. 다른 대안은 전부 "관련 자료를 보여준다"에 머무는데, 통계 대조는 "발언은 6%, 통계청 수치는 6.3%"처럼 근거와 일치/불일치를 기계적으로 말할 수 있다. 출처가 정부 공식 통계라 신뢰도 설명도 명확하다.

**한계와 확인할 것.** 주장 문장에서 "어떤 통계의, 어떤 시점, 어떤 항목"인지를 뽑아내는 게 어렵다. 지금의 규칙 기반 추출로는 이 매핑을 못 한다. 지표를 몇 개(소비자물가지수, 실업률 등)로 좁혀서 시작하는 게 현실적이다. 통계 갱신 주기와 발언 시점의 어긋남도 처리해야 한다.

**우선순위: 높음(범위 제한 조건부).** 전면 도입은 어렵지만, **지표를 2~3개로 좁힌 부분 구현이 데모에서 가장 인상적일 것이다.** "이 발언의 수치를 통계청 원본과 대조했습니다"는 다른 어떤 결과보다 설득력이 있다.

## A-4. SNU팩트체크

**무엇인가.** 서울대 언론정보연구소가 운영하던, 국내 언론사들의 팩트체크 기사를 모으는 플랫폼.

**확인된 문제.** 검색 결과 기준으로 **무기한 휴지에 들어갔다는 보도가 있다.** 시점과 현재 상태는 직접 확인이 필요하다. 공식 API 공개 여부도 검색으로는 확인되지 않았다.

**우선순위: 낮음.** 서비스 상태가 불확실하다. 다만 과거 축적분을 데이터셋으로 받을 수 있다면 한국어 팩트체크 판정 사례로서 가치가 있으므로, 문의는 해볼 만하다.

# B. 근거와 주장을 비교해 판정하는 수단

여기가 지금 완전히 비어 있는 부분이다.

## B-1. 한국어 자연어 추론(NLI) 모델

**무엇인가.** 두 문장을 입력받아 `함의(entailment)`/`모순(contradiction)`/`중립(neutral)`을 분류하는 모델. 한국어로는 KLUE 벤치마크의 NLI 과제로 학습된 공개 모델들이 있다.

**우리 구조에 어떻게 맞는가.** 이 세 결과가 MVP U-03이 정한 판정 세 종류에 거의 그대로 대응한다.

| NLI 출력 | 우리 판정 |
| --- | --- |
| 함의 | 근거와 일치 |
| 모순 | 근거와 불일치 |
| 중립 | 근거 부족 |

**이점.** 외부 API 호출 없이 컨테이너 안에서 돈다(비용·지연·키 발급 문제 없음). 우리 배포가 이미 CPU 추론 스택(faster-whisper, ViT 분류기)을 갖고 있어 추가되는 운영 복잡도가 작다. 판정의 근거가 "이 근거 문장과 이 주장 문장의 관계"로 특정되므로, U-02가 요구하는 "왜 지지·반박하는지"를 문장 쌍으로 제시할 수 있다.

**한계.** NLI 모델은 짧은 문장 쌍으로 학습돼 있어, 긴 기사 본문을 그대로 넣으면 성능이 떨어진다. 근거에서 관련 문장을 먼저 골라내는 단계가 필요하다. 그리고 **NLI의 "모순"은 "거짓"이 아니다** — 근거 자료가 틀렸을 수도 있다. 이걸 사용자에게 어떻게 표현할지가 설계 문제다.

**우선순위: 높음.** 지금 비어 있는 판정 단계를 외부 의존 없이 채울 수 있는 가장 현실적인 방법이다.

## B-2. LLM 판정 — 로컬(Ollama)

**무엇인가.** 주장과 근거를 함께 주고 판정과 그 이유를 생성하게 한다. 우리 코드에는 이미 Ollama 연동 자리가 있다(`deepcheck/vlm.py`).

**이점.** 판정과 **판단 이유 문장**을 동시에 얻는다. U-02가 요구하는 "이 자료가 왜 주장을 지지·반박하는지"를 직접 만족하는 유일한 방법이다. 근거 부족 사유를 U-03이 정한 다섯 가지(자료 없음·관련성 부족·시점 불일치·출처 충돌·신뢰성 부족)로 분류하게 하는 것도 이 방식이면 가능하다.

**한계.** CPU에서 돌릴 만한 크기의 모델은 한국어 추론이 불안정하다. 그리고 근본적으로, **LLM이 근거 없이 그럴듯한 판정을 만들어내면 우리 서비스는 우리가 막으려던 것과 같은 일을 하게 된다.** 반드시 "제공된 근거 안에서만 판단하고, 근거가 부족하면 부족하다고 답한다"를 강제하고, 생성된 이유 문장이 실제 근거에 있는 내용인지 검증하는 장치가 필요하다.

**우선순위: 중간.** 이유 생성이라는 고유 가치가 크지만, 잘못 쓰면 위험이 가장 큰 선택지이기도 하다.

## B-3. LLM 판정 — 외부 API

**이점.** 한국어 추론 품질이 로컬 모델보다 확실히 낫다. 주장 추출(T-07)의 한국어 종결어미 문제(구현 노트 T-6 참조)도 같이 해결된다.

**한계.** 비용이 요청당 발생하고, 지연이 응답 시간 목표(첫 결과 1분)에 직접 얹힌다. 해커톤 이후 계속 운영한다는 목표를 생각하면 비용 구조를 먼저 계산해야 한다. B-2와 같은 환각 위험도 동일하게 적용된다.

**우선순위: 중간.** 데모 품질을 가장 크게 올리지만, 운영 지속성 관점에서 결정이 필요하다.

## 추천하는 조합

지금 상태에서 가장 적은 작업으로 가장 큰 변화를 만드는 순서다.

1. **네이버 검색 API(뉴스)를 근거 제공자로 추가** — 발급이 가장 쉽고, 위키백과가 못 덮는 시사 영역을 즉시 메운다. 이것만으로도 근거 카드가 비어 있지 않게 된다.
2. **한국어 NLI 모델로 판정 단계를 만든다** — 외부 의존 없이 `근거와 일치`/`근거와 불일치`/`근거 부족`을 실제로 판정할 수 있게 된다. 지금 모든 결과가 판단 유보로 끝나는 문제가 여기서 풀린다.
3. **지표를 좁힌 통계 직접 대조를 하나 붙인다** — 소비자물가지수처럼 자주 인용되는 지표 하나만이라도 원본과 대조하면, 데모에서 보여줄 "진짜 검증" 사례가 생긴다.
4. **BigKinds는 신청 조건을 확인하고 병행 추진** — 되면 근거 품질이 가장 크게 오른다.
5. **Google Fact Check Tools는 키가 나오면 붙이되, 주력으로 기대하지 않는다** — 이미 검증된 주장에만 걸리므로 적중률이 낮다.

## 결정이 필요한 것

팀장 확인이 필요한 항목이다.

- 판정을 **자동으로 낼 것인가**, 아니면 **근거만 보여주고 판단은 사용자에게 맡길 것인가.** 지금 구현은 후자에 가깝다. 전자로 가려면 B의 어느 방법을 쓸지 정해야 한다.
- LLM을 파이프라인에 넣을 것인가. 넣는다면 로컬인가 외부 API인가. 비용·지연·환각 위험을 어디까지 감수할지가 정해져야 설계를 시작할 수 있다.
- 근거의 **출처 유형**(전문 기관 판정 / 뉴스 기사 / 백과사전 / 통계 원본)을 사용자에게 구분해 보여줄 것인가. U-02가 요구하는 항목인데 지금 구현에 없다. 위 대안들을 붙이면 출처 종류가 늘어나므로 이 구분이 더 중요해진다.
